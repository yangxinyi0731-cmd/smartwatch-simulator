# 模拟智能手表检测台（E0 前端演示）

更新时间：2026-08-31

## 定位

本页面把已经完成的 P0、P1、P2 工程基础做成一个可在 Windows 本机直接操作的模拟智能手表检测软件。现场评委可以从 105 组已登记案例中搜索、筛选和选择案例，在可见的手表界面上开始、暂停、继续或重置检测，并在同一屏查看四步判断过程与仓库已有结果。

本次仍以演示界面为范围，没有修改三个模型、数据合同或部署边界。WEDA-FALL 案例继续显示仓库已经保存的同源回放摘要；CAPTURE-24 和合成生活规律仍只显示案例输入已经登记，不包装成新模型成绩。为给结果增加可核对的判断依据，8010 本机服务新增一个只读证据接口：它核对现有 SQLite 案例登记和本机传感器文件后返回实际合量波形，或从固定种子合成事件生成规律时间图；它不运行模型，也不写入数据库。页面不是 P9，不具备现实环境中的提前几秒预测、现实报警或部署批准。

## 打开、停止和诊断

完成仓库 `README.md` 的首次安装后，在 `scripts\windows` 中使用：

- `start-early-risk-workbench.cmd`：启动并打开工作台；
- `stop-early-risk-workbench.cmd`：核对进程身份后停止；
- `diagnose-early-risk-workbench.cmd`：只读检查文件、依赖、E0 合同、安全边界和服务状态。

固定地址：`http://127.0.0.1:8010/`

健康检查：`http://127.0.0.1:8010/api/health`

运行状态和日志位于 `backend/runtime/early-risk-workbench/`，该目录已被 Git 忽略。启动脚本记录 PID、Python 绝对路径和启动时间；停止脚本必须三项一致才会停止进程，避免误停其他程序。

## 架构隔离

```text
版本化 YAML / JSON 合同与报告 ───────┐
现有 SQLite 案例登记与本机 NPY ─ 只读 ├─►
固定种子合成规律事件 ────────────────┘
research.early_risk.workbench_server
            │ 127.0.0.1:8010
            ▼
独立 HTML / CSS / JavaScript 模拟手表检测台
```

该服务不挂载到 `backend.app.main`，但会通过只读查询取得当前案例的登记元数据，并重新核对传感器文件路径边界、SHA-256、数组形状、`float32` 类型和有限值。前端只收到最多 240 个实际抽样位置对应的加速度合量，以及六轴案例的角速度合量；原始文件不进入 Git，也不被服务改写。服务不调用现有三个模型、不写 SQLite、不修改 Vue 产品界面，也不连接外部网络。两个本机界面只共享 `frontend/src/tokens.css` 中的视觉令牌值。

## 页面内容

### 首屏检测软件

页面使用深色应用侧栏、设备状态栏和浅色工作区。首屏固定显示三个协作区域：左侧案例库，中间模拟手表，右侧判断过程。评委不需要先读研究说明，就能直接选择案例并操作手表。侧栏五个入口都带有一句简体中文用途说明；桌面同排的“实时检测”和“案例回放”按用户点击的锚点保持唯一当前状态，不再争抢或重合。

主操作区下方新增完整宽度的“判断依据”。左侧动作图只说明案例类别和腕表位置，始终标注“不是参与者影像 / 示意图不作为判断证据”；右侧按案例类型显示真实传感器合量波形或合成规律时间图；最下方固定列出来源核对、连续输入、比较方式和当前结论。这样评委可以从结果继续向下核对“输入是什么、图里看到了什么、系统按什么规则比较、结论有什么限制”。

### 105 组案例库

案例总数和分类固定显示为：全部 105、受控模拟跌倒 40、受控日常活动 60、活动识别 4、生活规律 1。列表每页 6 条，支持按案例 ID、短标题或参与者搜索。切换类型或有效搜索后，如果原案例不再可见，手表与判断区会同步到首个可见案例。

### 模拟手表操作

手表显示当前时间、电量、案例编号、数据来源、采样率、传感器轴数、检测阶段、进度和结果。开始检测后按“读取腕部数据—整理连续窗口—独立模型判断—结果复核”四步运行；暂停、继续和重置只控制浏览器内的阶段状态，不启动真实传感器、不训练模型、不发送通知。

### 结果真实性

- WEDA-FALL 的 100 组案例显示仓库已经保存的“跌倒特征匹配度”和跌倒动作记录数；页面紧邻解释该数值只表示动作与受控跌倒动作有多相似，不是现实跌倒概率。受控模拟跌倒与受控日常活动分别标记，日常活动中的疑似误判不会被包装成现实风险。
- CAPTURE-24 的 4 组活动案例仍只把登记类别显示为“案例已就绪”，不冒充本轮新模型成绩；判断依据区读取对应的 20 Hz、400 个原始采样三轴文件，以实际加速度合量波形说明输入变化。
- WEDA-FALL 判断依据区读取对应六轴文件，把 X/Y/Z 加速度和角速度分别计算为两条合量曲线，并同时显示采样率、原始/显示采样数、登记标签区间和数据质量标记。合量峰值只描述输入变化，不被写成模型作出判断的单一原因。
- 100 天合成生活规律仍只显示合成输入规模和“规律规则已登记”；它没有腕部传感器流，因此依据区明确改用最近 14 天用餐、午睡和散步的事件时间图，不生成假波形。它不是参与者的生活记录。
- 检测完成后独立生成一段“结果分析”，根据案例类型、窗口规格、保存匹配度和保存记录解释为什么给出当前结果；保存资料没有逐轴原因时会明确说明，绝不虚构某一方向或身体部位异常。
- 三个现有模块保持独立，并分别用一句中文说明“检测跌倒动作相似性”“识别活动类型”“比较个人生活规律”，不合成医学风险分数。未来几秒风险预测显示“后端尚未接入 / 锁定 / 需要 P3–P9”。
- 案例人物在主要界面中统一称“参与者”；底层来源、案例 ID 和受控/自由生活/合成类型仍然保留，避免把数据类型混为一谈。

### 说明与边界

页面保留一个渐进展开的“说明与边界”区域，继续说明“先认识每位参与者的平常”、一天的生活路线、快速坐到沙发、坐车颠簸和摘表充电等未来产品要求。这些文字只解释目标和困难负样本，不冒充当前识别结果。页面始终显示 `prediction_evidence=false`、“只演示、不报警”和外部通知 0 次。

## 本机接口

| 方法 | 路径 | 用途 | 是否写入 |
|---|---|---|---|
| GET | `/api/health` | 核验回环范围、E0 和通知关闭状态 | 否 |
| GET | `/api/workbench` | 汇总版本化合同与报告供页面读取 | 否 |
| GET | `/api/case-evidence/{case_id}` | 只读核对登记文件并返回实际合量波形，或返回固定种子合成规律时间图 | 否 |
| POST | `/api/simulate` | 对固定策略输入执行一次 dry-run | 否 |
| GET | `/evidence/{allowlisted-name}` | 下载五类固定证据原件 | 否 |

所有动态响应使用 `Cache-Control: no-store`。服务设置 CSP、`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、同源资源和无引用来源等安全响应头。

## 强制安全边界

- 服务器拒绝绑定 `0.0.0.0`、局域网地址或公网地址；
- POST 请求上限为 16 KiB，只接受 `application/json`；
- 触发阈值、复位阈值、连续证据数和冷却期均有服务端范围检查；
- 策略端拒绝 `dry_run=false`；
- 证据下载使用文件名白名单并拒绝路径穿越；
- 案例依据编号限制长度并拒绝 `/`、`\` 和路径穿越；传感器文件必须位于项目目录内，且哈希、形状、类型和有限值全部匹配登记记录；
- 页面不使用浏览器原生 `alert`、`confirm` 或 `prompt`；
- 页面不使用本地存储保存参数，不把参数写入 URL；
- 页面没有真实个人数据、通知收件人、电话、短信、振动、声音、救援或部署入口；
- 外部通知计数必须为 0，否则启动与测试视为失败。
